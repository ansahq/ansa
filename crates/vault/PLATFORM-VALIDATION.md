# Vault platform validation (P03a / P03b)

## What is implemented

| Mode | Key custody | Evidence status |
| --- | --- | --- |
| Windows DPAPI | Existing current-user DPAPI, with UI forbidden | `NativeTested`: Windows regression suite |
| macOS Keychain | One 32-byte random key per profile, in the default user-domain file-based Keychain (normally login) | `NativeUnverified`: compile checks only; no Mac link or execution recorded |
| Linux Secret Service | One 32-byte random key per profile, in the provider's default persistent collection | `NativeUnverified`: compile checks only; no GNOME, KDE, or native headless execution recorded |
| Explicit passphrase | Random profile key wrapped with a passphrase-derived key; encrypted header and payloads on disk | `PortableTested`: exercised on Windows |
| Explicit memory-only | Random session key and sealed named secrets in process memory; no vault directory or file access | `PortableTested`: exercised on Windows; non-persistent by design |

`Vault::open(path)` only tries the native backend. Fresh profiles without usable secure storage receive an error and do not get a vault directory or plaintext alternative. Existing native profiles also return errors rather than constructing an empty or replacement vault. `Vault::open_existing(path, allow_prompt)` additionally refuses to create a missing profile. **Use the existing-only APIs when a separate application database already contains vault ciphertext**, even if the entire vault directory is gone.

- **macOS:** Security.framework generic-password item with service `dev.ansa.vault.v1` and account equal to the public `profile_id` from `vault.json`. The item is added to the user's default file-based Keychain with `SecItemAdd`, `kSecUseKeychain`, and no synchronizable or broad access attributes. Routine key reads and provisioning check the default Keychain's lock state with `SecKeychainGetStatus` and fail with `Locked` without UI. Routine reads also use `kSecUseAuthenticationUI = kSecUseAuthenticationUIFail`; `try_unlock` or prompt-enabled reopen skips the unlocked precheck and omits that key, so the item query may let Security.framework unlock or prompt for the default Keychain where the OS permits. A Keychain that remains locked still yields a typed failure. Whether the item query can actually unlock a locked default Keychain, and which UI it presents, is **not** verified. `SecKeychainGetStatus` and `kSecUseAuthenticationUIFail` are declared directly because `security-framework-sys` 2.17 does not expose them; their link-time presence and runtime semantics are **not** verified. No Touch ID, Secure Enclave, app entitlement, or custom ACL is requested. The item uses the OS default ACL/application identity; unsigned, ad-hoc, or re-signed builds may prompt or be denied. These synchronous calls have no application-enforced wall-time limit; keep them off the UI thread.
- **Linux:** Secret Service over the user D-Bus session (`secret-service` 5.2, negotiated DH/AES session, never the library's `Plain` transport). Items have label `Ansa Vault`, content type `application/octet-stream`, and public `application=ansa-vault` / `profile-id=<profile_id>` attributes. Provision only in the default collection, refuse a default aliased to `session`, create without replace, and verify key read-back before publishing metadata. Routine lookup searches all collections for exactly one matching item and never unlocks an item or calls a prompt API; a locked item reports `Locked`. `try_unlock` or prompt-enabled reopen may invoke the provider's locked-item unlock prompt; dismissed prompts are denied. Provisioning calls `ensure_unlocked` and then `create_item`. In the pinned `secret-service` 5.2.0, `ensure_unlocked` only tests the lock state (`collection.rs:49–59`) and does not itself prompt. **Residual:** even after that unlocked report the provider may require authorization and return a D-Bus prompt for `CreateItem`; `secret-service` 5.2.0 executes that prompt internally (`collection.rs::create_item`) and exposes no noninteractive create variant, so this crate cannot suppress it. The async operation is raced against a five-second deadline (30 seconds for prompt-enabled unlock), including connection and session negotiation; the deadline bounds the wait but cannot cancel an operation already delivered to the provider. Provider/session availability, prompt behavior, encrypted-session support, and DH interoperability have not been verified on GNOME or KDE.
- **Passphrase:** `Vault::open_passphrase(path, bytes)` creates or opens a separate passphrase vault; `Vault::open_existing_passphrase(path, bytes)` only opens one. No automatic backend conversion. Use a high-entropy passphrase chosen by the user, from a secret input buffer. The format fixes RustCrypto **Argon2id v19**, **64 MiB**, **3 iterations**, **1 lane**, a random **16-byte salt**, and a **32-byte output key** (no on-disk cost settings). The KDF key only wraps a random data key with XChaCha20-Poly1305. Bounds are 1–1024 passphrase bytes; the minimum is not a strength guarantee. The app cannot recover a forgotten passphrase. `lock()` discards the cached key; `unlock_with_passphrase(bytes)` requires the on-disk header to be byte-for-byte the one this handle opened or last rewrote, then authenticates that header again. A bad passphrase does not alter ciphertext or metadata. `change_passphrase(old, new)` applies the same exact-header requirement, authenticates the old wrapper, requires it to wrap the same data key the open session is using, validates both passphrase lengths, and atomically replaces the wrapper and salt without re-encrypting payloads. A replaced header — including a same-profile-ID wrapper for a different key, or an older backup header restored after this handle changed the passphrase — is rejected without installing its key or overwriting it. Restore the exact metadata or explicitly reopen to adopt a restored snapshot.
- **Memory-only:** `Vault::memory_only()` is pathless. `status().mode.is_persistent()` is `false`; consumers must hold history and its metadata in volatile storage, not write it to their database/WAL/index even in sealed form. `lock()` discards the in-vault map and destroys the session key; `try_unlock()` generates a fresh key. A second vault or a restarted process cannot read old payloads. The vault's named-secret map enforces 4,096 entries and a 16 MiB encoded byte limit; disconnected caller-owned caches need separate limits and wiping.

`status()` reports the selected mode, last-known state (`Ready`, `Locked`, or `NativeLocked(issue)`), and evidence level without touching the provider. An unsupported platform returns `VaultError::Unsupported` from the native open path. Availability, lock, access denial, lost key, invalid key and deadline outcomes use `VaultError::SecureStorage { issue }`. Native keys are not cached across operations. Loss or revocation observed by an open handle gates further operations until explicit unlock. Neither opening an existing profile nor unlocking it installs a replacement key. `unlock()` is retained for Windows/API compatibility; new callers should prefer fallible `try_unlock()` or `unlock_with_passphrase()`.

Format-2 handles are bound to the exact `vault.json` bytes they opened. If metadata is removed or replaced while a ready handle is open, secret and payload operations fail with `MetadataMissing` or `InvalidVault` until the original metadata is restored or the vault is reopened; a locked or native-denied handle reports its lock/denial first. Passphrase `unlock_with_passphrase` and `change_passphrase` also require the exact snapshot, so a restored older header or a same-ID wrapper for another key cannot be adopted or overwritten by the live handle. `status()` and `lock()` remain local session operations. This prevents an open handle from writing ciphertext under a stale profile after a restore or concurrent credential change. Invalid aliases, contexts and oversized inputs are rejected before the native keyring or cached key is touched. Resolution prefers an exact-case file; if a case-sensitive filesystem contains multiple case variants for a non-exact lookup, the operation fails closed rather than deleting or replacing an arbitrary file. On a case-insensitive filesystem the variants name one entry and no ambiguity exists; the Unix regression test detects the actual filesystem behavior before choosing a branch.

## Format, maintenance and recovery

- DPAPI metadata (`format: 1`, `backend: windows-dpapi-v1`) and payload version 1 remain unchanged. New persistent backends use `format: 2` in `vault.json`, a mode-specific backend identifier, random 128-bit public `profile_id`, a native AEAD key check or authenticated passphrase-wrapped data key, and exact-byte header binding in memory. Only passphrase mode has `salt`. Unknown/incorrect formats or modes are rejected. A non-empty format-2 vault directory with missing metadata is not a fresh profile.
- Legacy Windows compatibility exception: `Vault::open` on Windows may recreate the non-secret format-1 `vault.json` when it is missing, because DPAPI ciphertext is bound to the Windows user rather than to that metadata. `Vault::open_existing` still refuses missing metadata, and `verify_backup` requires it. Format-2 backends never recreate metadata.
- The payload JSON shape is still `{version, context_tag, ciphertext_hex}`. Non-DPAPI modes write version 2: lowercase hex of **24-byte random nonce || ciphertext || 16-byte authentication tag**, using RustCrypto XChaCha20-Poly1305. Associated data binds a versioned domain, the profile ID and the exact validated context; named-secret contexts include the normalized (lowercase) alias. Metadata authentication and payload authentication use separate domains. Do not put sensitive values in aliases, paths or context labels. These backends do not decrypt DPAPI blobs or implicitly migrate data across modes.
- `rotate()` reads and authenticates each named secret, then re-seals it under the existing profile key with fresh randomized encryption, atomically replacing each file. It verifies the current header first. A process crash can leave a mix of old and refreshed ciphertext or a stale encrypted temporary file; prior files are not removed before their replacement is committed. `change_passphrase` requires an exact-snapshot match and updates the in-memory header snapshot only after a successful authenticated read/write; `unlock_with_passphrase` accepts only the exact snapshot already held and never rewrites it. Neither operation rotates OS master keys, revokes old backups or rotates the payload data key. Suspected compromise of a native or payload key requires a separately provisioned profile and explicit, authenticated re-sealing by the consumer, not `rotate()`.
- Back up the complete encrypted `vault.json` and `secrets/` directory and any external sealed-payload store as one consistent snapshot (stop writers; capture the database and its WAL consistently). Protect the original native key item via the platform/provider's backup mechanism separately, or retain the passphrase matching the backed-up header. This crate does not export native keys or automate OS keyring backups. Restore into a separate directory and open with the original mode and credentials. Reopen after replacing a vault directory in place. Call `verify_backup()` and compare the returned verified count with the expected inventory; authenticate external records with `verify_payload(payload, context)`. `verify_backup()` also requires the current header/metadata (exact bytes for format 2; format/backend for Windows), so a missing or replaced header is not reported as a good backup. It still checks authenticity, not completeness or rollback; an empty directory with a valid header does not prove a nonempty backup was fully restored. Same-provider restore across users/machines is not guaranteed.
- If native authorization is removed, restore access to the same item, then `try_unlock()` or `open_existing(path, true)`. If the item is lost, restore the matching original item and metadata from a protected backup; do not create a new item with the same name. If the only copy of the key is gone, the old ciphertext is unrecoverable. Keep it intact and initialize a *new* vault at a different path if the user chooses to start over.
- All reads and writes are bounded at the vault boundary (1 MiB plaintext, 3 MiB sealed file, 4 KiB metadata, bounded names and directory scans). The native item must be exactly 32 bytes; OS/D-Bus libraries can allocate response buffers before that size check. File publication uses an exclusive temporary file, file sync, then rename, or a same-directory no-clobber hard link for a new header. Newly created Unix vault and `secrets/` directories use mode `0700`; metadata, payload and temporary files use mode `0600`. Existing directories are not chmod'ed. Directory-entry sync is best-effort: macOS and some filesystems reject directory `fsync` (for example `EINVAL`/`ENOTSUP`), so commit success is never turned into a post-commit error. No stronger arbitrary-power-loss guarantee is claimed. Use a single active writer and a private, dedicated profile directory. Initial OS registration precedes metadata publication; a crash or racing creator can leave an orphan native item, never a replacement for an existing profile. Native items are intentionally not auto-deleted by this crate.
- Deletion removes the ciphertext file but does not securely erase storage, journals, snapshots or backups; old ciphertext remains decryptable with the same key. There is no secure-erase claim.

## Threat model and caller responsibilities

Protects confidentiality and integrity of secret bytes against disclosure of application files and against unauthenticated changes to ciphertext, context or profile binding. It does not protect against malicious code running in the unlocked app, a compromised OS or root, a malicious keyring or session bus, or other same-user applications allowed by provider policy. It does not guarantee confidentiality from a process debugger, swap, hibernation, full memory/core dumps, OS diagnostics, or dependency/OS-managed memory. Rust-owned key and plaintext scratch buffers and the Argon2 workspace are zeroized on drop; native API, Secret Service, Keychain, zbus and other dependency copies are not under this crate's control.

The header snapshot and exact-byte checks assume a single writer. They detect metadata replacement between operations but not a race during a single external write. A private vault directory is assumed: reads check `symlink_metadata` before opening, but a same-user attacker able to replace entries between that check and `open` could cause a read or blocking open of another file; authenticated decryption still fails closed and never returns unauthenticated plaintext. Directory scans, names and payload sizes are bounded, but a same-user attacker can still deny service.

Revocation or lock cannot recall bytes or a key already loaded by an in-flight operation. Native key loss is unrecoverable without the original OS item; this crate does not add a recovery key. Windows DPAPI v1 payloads are user-bound but not bound to a vault directory/profile: any same-user DPAPI caller, and a ciphertext copied to another DPAPI vault used by the same user with the same context, can unprotect it. Native format-2 payloads are bound to the random profile ID. macOS item ACL semantics and Linux Secret Service provider policy determine which same-user processes can read the key item; this crate does not add an application-level ACL. The Linux DH session is not an authenticated provider identity and runs over the user session bus. The existing `Vec<u8>`-returning compatibility APIs leave plaintext ownership with their caller; `get_secret_zeroizing` and `open_payload_zeroizing` return a wiping, redacted `SecretBytes`.

No library code writes secrets, keys or passphrases to logs, command arguments, environment variables, SQLite, or an index. Sentinel tests check vault files, serialized payloads and redacted diagnostics. They do **not** attest to the entire application's database, WAL, previews, search, logs or OS crash dumps. Those remain integration/host validation, and caller processes must not log exposed plaintext or add sensitive names to metadata.

## Validation performed on this host (not native acceptance)

Host: Windows 11 `10.0.26200.9974`, `x86_64-pc-windows-msvc`, rustc `1.99.1` (`58cf8f9c3 2026-10-13`), cargo `1.99.1`. All test/check/clippy commands used `--locked --offline`; `cargo fmt --check` does not accept those flags. No dependency resolution or lockfile update occurred. No native Keychain or Secret Service host was available.

Final-review fixes in this revision:

- Passphrase `unlock_with_passphrase` and `change_passphrase` now require the on-disk header bytes to equal the session's exact snapshot before unwrapping or writing. A same-ID wrapper for another key and an older restored header are rejected; unlock leaves the handle locked with no key installed, and change leaves the wrapper untouched. Explicit reopen still adopts the on-disk header.
- macOS interactive `load` skips the default-Keychain unlocked precheck so the item query can recover or prompt where Security.framework permits; routine noninteractive loads keep the precheck plus `kSecUseAuthenticationUIFail` and stay silent. Provisioning keeps the precheck.
- The Unix case-variant test probes the filesystem and uses single-entry assertions on case-insensitive volumes (macOS APFS default) instead of assuming `#[cfg(unix)]` implies case sensitivity. The two-file ambiguity branch remains for case-sensitive filesystems.
- Linux routine reads still call no unlock/prompt API. The `CreateItem` prompt residual after an unlocked report is documented; no D-Bus fixture was added.
- **Transactional volatile replacement (R3).** `Vault::put_secret_replacing(alias, secret, remove_aliases)` is the memory-only replacement transaction used by the clipboard. It validates the target and every removal alias, seals the new payload first, computes the exact encoded-byte and secret-count totals after subtracting the removals, and only then mutates the map. A quota, count, alias or cryptographic failure leaves every existing payload — including the ones named for removal — untouched. File-backed vaults return `WrongMode`. `MemoryStore::put_replacing` performs the same check-before-mutate accounting, and `put_secret` now shares it.
- **macOS interactive recovery (MEDIUM 3).** If an interactive Keychain item query fails with a mapped `AccessDenied` while `SecKeychainGetStatus` still reports the default Keychain locked, `load` now returns the typed `Locked` issue instead of a generic denial. The lock-status recheck function is evaluated on every query failure, including routine noninteractive failures, because its argument is evaluated eagerly; the returned issue changes only for `interactive && AccessDenied && locked`, and routine results or provisioning otherwise keep their existing mapping. The typed `Locked` issue only reports the locked state; it is not itself a full system-unlock instruction. The mapping helper is a pure unit test and does not call Security.framework.

The host suite exercises real Windows DPAPI, passphrase and memory-only storage plus a fake native-key provider. Fake-provider unit tests cover denied/locked/missing/invalid/timeout outcomes, unchanged header and ciphertext, no replacement key on existing-vault failure, no metadata publication after failed read-back, wrong mode/malformed/oversized headers, post-open header removal or replacement, and validation before provider access. Passphrase regression tests cover a same-profile-ID wrapper for a different key rejected by both unlock and change, a locked handle refusing an older restored header while staying locked and leaving the restored header untouched, recovery only after restoring the exact opened bytes, and normal change/reopen still working. One new portable fixture fills a memory-only vault to within 4 KiB of its encoded budget, proves a failed 128 KiB replacement leaves the victim and unrelated secrets readable, then proves a fitting replacement evicts exactly the named alias; a passphrase-backed fixture proves `put_secret_replacing` returns `WrongMode` without mutation. The macOS-only unit tests for the interactive-access policy and the interactive-denial-to-locked mapping were compiled by the macOS target check but **not executed**; they do not link or call Security.framework. No Linux prompt regression test was added: exercising a provider-returned `CreateItem` prompt requires a D-Bus Secret Service fixture, so that residual is documented rather than asserted. Unix-only tests for `0700`/`0600` permissions, symlink refusal and ambiguous case-variant aliases were compile-checked for both Unix targets but **not executed**. The case-variant test probes the actual filesystem and uses the single-entry assertions on case-insensitive volumes; the two-file ambiguity branch runs only on case-sensitive filesystems (for example the Linux runner; macOS APFS normally takes the other branch). The Linux and macOS targets were also clippy-checked; this is not native acceptance.

Residual risks for these fixes:

- The transactional API is memory-only and has no cross-process guarantee; a memory-only vault is process-local by design. A crash after the vault replacement but before the consumer commits its own metadata is the consumer's problem. The clipboard's volatile store keeps history only in memory, so a process crash discards it rather than leaving disk metadata to reconcile; native execution was not available.
- The macOS recheck only changes the returned issue for a mapped `AccessDenied` while locked; other provider outcomes keep their original mapping. The status recheck call itself is still evaluated on every query failure, including routine ones. Whether a locked default Keychain actually returns `errSecInteractionNotAllowed` for the interactive item query, and whether `SecKeychainGetStatus` observes the same state immediately afterward, is **not** verified. The direct `SecKeychainGetStatus` symbol is still unverified at native link time.
- The Linux `CreateItem` provider prompt after an unlocked report remains possible and is **not** fixed by this pass; `ensure_unlocked` only tests lock state in the pinned `secret-service` 5.2.0.

## Native evidence still required

Run on macOS with real signed-app identity and a user Keychain, on Linux GNOME Keyring and KDE KWallet implementations with a real user session, and on native Linux without a keyring. Run `cargo test --locked -p ansa-vault` on each. The opt-in smoke tests can be run separately:

```text
cargo test --locked -p ansa-vault --test native native_keyring_round_trip_and_backup -- --ignored --exact
cargo test --locked -p ansa-vault --test native no_keyring_profile_never_silently_downgrades -- --ignored --exact
```

Use an isolated test account and remove the test `Ansa Vault` items using the native keyring tool afterward. Test locked collection/Keychain, grant and deny authorization, revoke authorization or remove the test item's key while the app is running, verify failure is typed and sealed files and `vault.json` are unchanged, restore the original item, explicitly unlock, and verify both named and external records from a backup. Explicitly test the macOS direct symbols (`SecKeychainGetStatus`, `kSecUseAuthenticationUIFail`) at link time and record OS/signing identity/ACL and no-UI behavior. With the default/login Keychain explicitly locked, record whether `open_existing(path, true)` or `try_unlock()` recovers through Security.framework or returns a typed failure, which UI (if any) appeared, and confirm routine `open_existing(path, false)` and key reads stay silent. Exercise app/process termination during a write and rotation, checking that no temporary, database, WAL, index, application log or crash-report fixture contains the plaintext sentinel. For Linux, separately report the GNOME/KDE provider and version, session type, DH support, and headless/no-provider configuration. Use a D-Bus fixture that returns a `CreateItem` prompt after reporting the collection unlocked (or a real authorization-requiring provider) to record whether routine open calls `Prompt` and whether provisioning does. For macOS, record OS/architecture, signing identity/ACL behavior, and whether directory `fsync` is rejected. Cross-compilation, fake-provider tests and the Windows host suite cannot substitute for any of these.
