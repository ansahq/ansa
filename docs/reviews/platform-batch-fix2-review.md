# ANS-82–99 — second-round fix verification

**Do not merge on code grounds.** The Carbon ABI and the Linux test are fixed. The specific X11 routing and Linux post-lock handoff fixes are in place, and the production memory-only prefill regression passes. The X11 drain can still lose an ownership generation, and a failed capture can still delete valid history when the test/embedding constructor combines disk metadata with a volatile vault. Native acceptance remains **0/8** and is not part of this verdict.

## Per-item verdicts

1. **R1 Carbon ABI — RESOLVED.** The [SDK header](https://github.com/phracker/MacOSX-SDKs/blob/master/MacOSX11.3.sdk/System/Library/Frameworks/Carbon.framework/Versions/A/Frameworks/HIToolbox.framework/Versions/A/Headers/CarbonEventsCore.h) declares both functions as returning `EventTime` (`double`, seconds since startup); Rust uses `f64` for both. Adjacent `ItemCount` and `ByteCount` are `unsigned long`, matching `usize` on macOS LP64. `crates/platform-api/src/hotkey.rs:229–243,259–294,354–396` converts both readings to monotonic nanoseconds, samples the fence after save and before enabling, and rejects `<=`. Rounding can merge nearby timestamps, not invert them; ties intentionally fail closed. Saturation starts at about 584 years of uptime. Invalid event time becomes zero and is rejected; an out-of-contract invalid **clock** sample would also become zero and weaken the fence, but the SDK documents no such return. A non-secure pre-fence press sets `down` before the gate and release clears it (`crates/platform-api/src/hotkey/macos.rs:63–69,105–174`). Linux and Windows still use timestamp-free `call()` (`hotkey/x11.rs:53–66`, `hotkey.rs:267–271,594–602`). The fence fixtures passed with supplied times; no Carbon callback/release or Mac linking was exercised.

2. **HIGH 2 same-XID X11 reassert — PARTIAL.** `crates/clipboard/src/linux/x11.rs:119–168,199–246,515–536` checks the void grab cookie, queries the owner, and drains XFixes while grabbed. Pinned x11rb 0.13.2 (`cookie.rs:100–104`, `rust_connection/mod.rs:326–346,653–675,679–699`) flushes the checked request and inserts a `GetInputFocus` sync when needed. The explicit flush after `check()` is redundant; the owner reply is also an ordering barrier. An accepted reassert processed before the grab has already queued its notification ahead of the reply. A matching same-XID event normally returns `ClipboardChanged`, advances the generation, and sends zero new conversions. No `SelectionNotify` for this conversion can be discarded: `ConvertSelection` has not been sent. Convert and ungrab are ordered on one connection; release is flushed, and I/O errors marked dead close the connection. A peer request not yet processed is not covered by the barrier. The grab binds the server's recipient, not bytes a same-window provider chooses from its own mutable state.
   - **New MEDIUM — event-bound loss.** Queue exactly 4,096 events after the last sync and before the grab takes effect, including the only notification for a same-XID reassert. `drain_selection_events` consumes the notification but returns `CaptureLimit` at the bound, dropping its `reasserted` flag. `transfer` bumps generation only for `ClipboardChanged`. The following `sync_selection` sees the old XID and no notification; the next screened copy can reuse the old sequence and be dropped as a duplicate. No conversion escapes on the capped call. Preserve the invalidation on the capped path or stop at the first matching event. The bound caps application drain iterations, not the queue x11rb buffers while waiting for replies.
   - Fake-server cases (`x11.rs:966–1036`) check zero conversions for the same-XID/changed-XID aborts and old-recipient routing on release, with a no-grab negative control. They stub the real drain and do not exercise the cap, `Reader` generation, or wire ordering. Linux compile/lint only.

3. **HIGH 3 Linux opener — PARTIAL; both reported wait/helper interleavings are closed.** `crates/platform-api/src/linux_native.rs:141–164,167–262,367–379,613–633` reuses the checked document, and captures one fallback directory before `ShowItems`. A failed `ShowItems` leads to revalidation of that same directory before and after the handler query; it then goes to the same checked opener as documents. The final closure runs under the shared child lock, immediately before `spawn`. Injected tests cover replacement during handler queries, retargeting inside failed `ShowItems`, and the lock being held when validation runs (`:666–814`); the lock fixture is not a real concurrent handoff test.
   - **Remaining MEDIUM — transient replacement can misbind MIME.** `crates/platform-api/src/opener.rs:186–269` stamps the leaf objects, not their ancestors. In an inert file-type query fixture, temporarily swap the parent so the query sees a different `.txt` with an allowed MIME, then restore the parent before returning. The original leaf was never moved or changed, all rechecks can pass, and the opener is called for a file whose MIME was not the one screened. This is separate from the post-check window and is not evidence of native execution of unsafe content.
   - `HOST-VALIDATION.md:210–216` honestly says the final `xdg-open` pathname handoff is not atomic: the helper/handler can resolve a changed path after the check. Successful `ShowItems` also passes only a pathname URI. The earlier blanket rejection claim (`:63–65`) needs the same qualification.

4. **R2 Linux regression test — RESOLVED.** `linux_native.rs:667–708` replaces the allowed file during the second query with a symlink to `no-extension`. `LocalTarget::capture` follows it and `safe_document` rejects the actual extensionless file (`opener.rs:196–223,346–353`). The test checks `is_err()`, exactly two queries, and zero opener calls; it no longer compares error text. Linux compile-checked, not run.

5. **R3 transactional eviction — PARTIAL overall; production memory-only repro resolved.** `crates/vault/src/lib.rs:663–685,1027–1082` validates and seals before any removal, computes count/bytes in locals, and commits under the session mutex (`portable.rs:357–390`). Quota/count/crypto errors cannot change payloads or the byte counter. Each existing lowercase removal key is subtracted once; case-variant duplicates, missing aliases, and a victim equal to the target are safe. Replacing a target retains its original spelling and uses a lowercase authenticated context. The vault fixture proves byte-quota rejection and a successful replacement; count and crypto failure ordering were source-checked. `crates/clipboard/tests/vault_modes.rs:80–142` runs the real `ClipboardStore::open` prefill case: 4 KiB free, `max_items=1`, small row stored, 128 KiB skipped, same ID and plaintext still readable, no disk writes.
   - **Remaining MEDIUM — failed embedded capture can still lose a valid row.** `crates/clipboard/src/store.rs:1021–1105,1500–1527,1673–1704`. Use `open_with_backend` with a volatile-budget backend and two valid rows. Allow reduced-history pre-commit and successful `seal_replacing`, then fail the final history write: capture returns an error, deletes the new alias, and cannot restore the already-deleted victim. Alternatively, reject the seal and fail the rollback history write. Rollback I/O errors are ignored (quota can still return `Skipped`); a later `reload_index` sees the reduced nonempty history and orphan cleanup deletes the still-valid victim. Neither path applies to ordinary `ClipboardStore::open` with a memory vault, where persistence is a no-op. Test both injected write failures or disallow the mixed configuration.
   - **Legacy aliases** (`store.rs:996–997,1061–1067,1115–1121`): only namespaced victims enter the transaction. A legacy alias still counts toward both limits and can cause a clean quota skip; cleanup is after success, not capacity available to the transaction. Fresh volatile stores never migrate legacy rows. The inherited best-effort deletion by legacy ID is also not ownership-checked: a successful eviction of row 1 can delete a preloaded unrelated `Ansa-Clip-1` (case-insensitive). Do not count such aliases as victims without proving ownership.
