## Native session and evidence setup

1. **Identify the build.** Use the exact proposed release executable for each native Rust target (an unpromoted experiment can diagnose, not accept). Build from a clean checkout using a fresh target directory; record `git rev-parse HEAD`, empty `git status --porcelain`, exact build command including target, features and profile, renderer pin/revision and adapter, fixture revision/configuration, actual launch argument array, absolute executable path and SHA-256 (`shasum -a 256` on macOS, `sha256sum` on Linux). Preserve the build log and identical executable bytes. The release owner independently hashes the final executable to be shipped for each target; a source commit match does not prove that an unsigned build, a debug build or a differently configured release is the shipped executable. Link the renderer promotion decision for AT; for glass link the build decision identifying the proposed app artifact. Do not use `--smoke-test`, `--interaction-smoke-test`, or any mode that dispatches input instead of a person.
2. **Isolate session data.** On an authorized test workstation use a fresh test account/profile and a pasteboard dedicated to test strings (or type them). Do not read personal clipboard history, private windows, notifications or files. Use inert actions and fixture-only data for all potentially consequential steps. Use fixture mode to isolate discovery where appropriate, but also verify J1 and focus return in the normal launcher startup path. Reset fixture state between journeys and between testers. An unreachable surface is `not-run`/blocking, not a substituted pass. Record focus and hotkey failure independently; use the supported fallback launch path, not an invented shortcut.
3. **Record exact native configuration.** Record full OS version and build/image, physical hardware model/architecture, display type, resolution/scale, locale/input method, contrast and reduced-motion modes. For Linux also record distro, kernel/image build, desktop/session and compositor versions, Orca and AT-SPI versions, speech backend and adapter flags. For macOS record VoiceOver build/version (or explicitly bundled with the named OS build), voice, verbosity, keyboard layout and modifiers. Keep run ID, tester identity/role, implementation involvement, start time and timezone. Preserve exact key chords and user-visible settings.
4. **Capture the native outcome.** Both testers independently start their own process and capture their own native artifacts on the same build and **identical declared configuration** (same target, executable bytes, OS build, hardware/display, locale, renderer, fixture and non-executable baseline launch arguments; local install paths may differ). At least one did not implement the change. Save unedited in-scope speech logs or native audio plus timed notes, and the native text probe for each AT run; also save an AT-SPI trace for Orca. Document recording format, duration, per-step timestamps or log lines, exact utterances, focus, and expected vs. actual result, including silence or duplicate speech. A screen recording without AT speech, keyboard scripts, Accessibility Inspector/Accerciser trees alone, or regenerated transcripts are not primary AT evidence. For glass, preserve native capture sequences on real hardware with a separate measurement log and both testers' notes; a staged/mock screenshot or modeled palette contrast is not acceptance. Record startup variants required by G4 in the measurement log and observations; the run's `launch_argv` is the baseline acceptance launch.
5. **Handle failures openly.** File a risk with owner, severity, build/configuration, source artifact locator, missing semantic/state, mitigation, blocking status and next verification. Keep failed runs and decisions in the external QA record. Retest after fixes on the newly identified build; any once-failing journey must repeat on a second day. Disagreement stays failed until reproduced and resolved. Both testers rerun the complete impacted matrix on the final build; a third person acting as release-gate reviewer checks identities, raw recordings and probe results before approving.

## Ledger and release handoff

```sh
python scripts/platform_acceptance_gate.py --check
python -m unittest discover -s scripts -p test_platform_acceptance_gate.py -v
python scripts/platform_acceptance_gate.py --require-accepted
```

`--check` is the CI/pre-merge mode: it validates schema, local bytes, reuse separation and ledger consistency, and succeeds on a valid **blocked** ledger. For this gate, CI runs only `--check` and the unit tests. It does not launch Ansa, a screen reader, a VM/emulator, or a physical Mac/Linux desktop, so a green CI job is **not** native acceptance and cannot itself change the 0/8 result. `--require-accepted` exits 1 for a valid ledger with any unaccepted profile; malformed, inconsistent or tampered evidence exits 2 in either mode. When all eight rows are otherwise accepted, `--require-accepted` still requires `--expected-commit` to match the ledger before it reports acceptance; without that binding it exits 2. Use `--ledger` and `--artifact-root` for a separate authorized QA evidence bundle; artifact root defaults to the ledger directory. For release use:

```sh
python scripts/platform_acceptance_gate.py --require-accepted \
  --ledger "$QA_ROOT/evidence.json" --artifact-root "$QA_ROOT" \
  --expected-commit "$RELEASE_COMMIT" \
  --review-record "$RELEASE_OWNER_DIR/native-approvals.json" \
  --binary-manifest "$RELEASE_OWNER_DIR/shipped-binaries.json"
```

Both release-owner files must be regular files that are not multiply linked, must resolve **outside** the QA artifact root, and must come from independent access-controlled storage; hardlinks are rejected. Both must declare the same full `candidate_commit` as the ledger; a mismatch is rejected. The binary manifest is `{"candidate_commit": "<full commit>", "binaries": {"aarch64-apple-darwin": "<lowercase SHA-256>", "x86_64-unknown-linux-gnu": "<lowercase SHA-256>"}}`; fill one digest per tested Rust target/architecture, using the exact final executable after any signing/package transformations. Every recorded run's target must match its native OS/architecture, and the measured executable digest must match the manifest for that target. No profile becomes accepted without both the independent approval and this binary binding. An acceptance applies only to the target, OS build, hardware and desktop session recorded for the profile; listing additional binaries in the manifest does not test them. This gate cannot close project-wide F08/F10.

- The ledger has an exact versioned schema enforced by [the validator](../scripts/platform_acceptance_gate.py). `candidate_commit` is null until a specific clean build is declared; it must match every submitted run and both external records. `non_native_context` is separate from `tickets` and never satisfies a profile. Each profile has exactly `blockers`, `runs` (zero to two final current records) and `review` (null until the release owner records the native review; null means none). `run_id` must be unique across the whole ledger. Keep superseded runs in the external QA record, not in this ledger or the release-owner approval file.
- Each run is `physical-native-manual`, with `run_id`, `tester_id`, `implemented_change`, `started_at` ISO timestamp with offset, profile-specific `configuration`, `build`, `artifacts`, and `results`. For each required J/G result give `outcome` (`pass`, `fail`, or `not-run`) and an `observation` pointing to the relevant timestamps and expected/actual behavior. Configuration, non-executable baseline launch arguments, renderer/fixture and executable-byte identity must match **exactly** within each pair of independent runs; local executable install paths may differ when the bytes and target match. Exact fields are listed in `configuration()` and `validate_run()`; the key set is fixed, so record ancillary settings such as display brightness/HDR, keyboard layout, VoiceOver voice/verbosity or kernel image in the relevant free-text value, observation or artifact.
- Build fields include clean status, matching commit, Rust `target`, renderer/fixture identity, promotion reference, binary and build log. `launch_argv` is the baseline acceptance launch: an array starting with the exact `binary_path`, followed by literal arguments; the gate rejects startup and interaction smoke flags, and both runs in a pair must record the same non-executable arguments. Record G4's variant startup launches in the measurement log and observations. Every file ref is `{"path": "normalized/relative/path", "sha256": "<64 lowercase hex>"}` and must be nonempty and verify under the QA artifact root. Primary artifact bytes must be unique across the whole ledger and cannot reuse the content of any build log or binary; within a run, binary and build-log bytes must also differ. AT artifacts are `tester-notes`, `native-text-probe`, and `native-speech-log` and/or `native-speech-audio`; Orca also needs `native-atspi-trace`. Glass artifacts are `native-visual-capture`, `measurement-log`, `tester-notes`; bundle multiple original captures in the visual artifact and keep references to specific captures.
- Glass runs also carry `measurements` with `tint_alpha`, `contrast` (case IDs such as `dark-black-caret`, with `foreground`, `background`, and `capture_locator`) and `bounds` (one series per case in `BOUNDS_TRANSITIONS`). Each sample is a `{"state": "<transition-label>", "rect": [x, y, width, height]}` object. For G3 each theme requires exactly `initial-on`, `cycle-1-off`, `cycle-1-on`, through `cycle-3-off`, `cycle-3-on`; G5 similarly requires `initial-dark` and three labeled `light`/`dark` pairs per glass state. The gate rejects extra samples and out-of-order labels; passing journeys additionally require the full labeled series and unchanged bounds, and the gate recalculates contrast. Record additional exploratory toggles in observations, not as extra series samples.
- Two complete passing independent runs with no unresolved blockers produce **REVIEW REQUIRED**, not acceptance. The gate prints the digest of `[ticket, profile, runs]`. The release owner must inspect actual provenance, raw files, coverage and risks, record a durable access-controlled decision, and add `review` with `source: release-owner-native-review`, `reviewer_id` distinct from both testers, `reviewed_at` after both runs, `decision_ref`, and `evidence_sha256` equal to that printed runs digest. The gate then reports **REVIEW UNVERIFIED** and prints `fingerprint(review)`. The release owner supplies `--review-record` from separate owner-controlled storage, with `candidate_commit` and `approvals` mapping `ANS-88/macos-14`-style row IDs to those printed **review-object** digests. Supplying only the approval, with a matching `review` present, gives **BINARY UNVERIFIED**; supplying only the binary manifest gives **REVIEW UNVERIFIED**; **ACCEPTED** requires both. Do not source either file from the evidence bundle or the tester. Changes to the fingerprinted runs or review invalidate approval, and any commit mismatch is rejected. The validator checks structure, local bytes and decision binding; it cannot authenticate arbitrary media, tester identities or the storage provenance of files passed on the command line. Never approve test fixtures, CI/startup artifacts, tree dumps, modeled measurements, or synthetic or reconstructed media. A valid JSON file by itself is not proof of a native run.
