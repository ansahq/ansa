### HIGH detail

**H1 — uncertainty is scoped to the token, not the operation/target.**

`prepare` always allocates a fresh sequence and inserts a new `PreparedRecord`
(`registry.rs:205-216`). `execute`'s replay guard is
`self.action_operations.get(&action)` (`registry.rs:370-389`), keyed by the exact
`ActionRef`. Reproduced:

* Probe A: two `prepare` calls for `app:demo`, both authorized and executed →
  `host_performs=2`, both `Completed`.
* Probe B: execute returns `Uncertain`; replaying the same authorization returns
  `ActionError::Uncertain` (host performs stays 1); then a fresh prepare + authorize +
  execute of the same command succeeds → `host_performs=2`. `reconcile` remained
  `StillPending`.
* Probe M: re-`authorize` on an already completed action returns `Ok`; only `execute`
  returns `Conflict`.

Impact: an upper layer that re-prepares a command after an uncertain result (a plausible
UI retry after the panel is reopened, or a catalog/entry refresh) silently performs a
second effect. The ticket's "not silently retried" intent and the reconcile doc
(`registry.rs:495-500`) are not met at operation/command scope. The docs in
`lib.rs:22-23` and the test name at `registry.rs:1107` imply broader protection than
exists.

Minimal fix: retain unresolved `Uncertain` operations by `(command_id, target identity)`
(or by command) and make `prepare` fail/return the pending `OperationId` until
`reconcile` resolves it; if concurrent actions are wanted, require an explicit
idempotency key and document it. Add a test that prepares again after `Uncertain`.

**H2 — kind does not imply its capability (or its consequence).**

`validate_spec` (`registry.rs:530-562`) only validates the capabilities the spec itself
declares. `CapabilityCatalog::builtin` contains one obvious capability per kind
(`grant.rs:11-24`), but nothing uses that mapping. Probe G registered:

* `quicklink:no-cap` with `CommandKind::Quicklink` and no `.requiring(...)` →
  `requires_confirmation=false`, executes with `GrantSnapshot::none()`.
* `script:no-cap` with `CommandKind::Script` and no capability →
  `requires_confirmation=true`, executes with `GrantSnapshot::none()`.

`CommandKind::is_consequential` (`command.rs:78-80`) marks only `Script` and
`Extension` as consequential; `Application { path }` (an arbitrary executable path) and
`Quicklink` are considered inconsequential "navigation". Combined with H3, an untrusted
provider can register an Application command to an arbitrary executable with no
capability and no confirmation.

Impact: the registry's grant re-check is vacuous for under-declared commands, so it
cannot be the "single execution path" permission boundary the docs describe. The
`grant.rs` claim that an unknown capability "fails registration instead of silently
running without a policy entry" only covers typo'd *declared* names.

Minimal fix: enforce a minimum capability set per kind at registration (or derive it
from `CommandKind`), reject a spec that omits its kind's capability, and decide
consequence from effect/kind policy rather than only Script/Extension. If policy is
intentionally delegated to the host, remove the enforcement claims and document that
the registry is not a permission boundary.

**H3 — command origin/provenance is not modeled.**

`register_raw` (`registry.rs:102-120`) parses an untrusted raw ID and accepts the
provider's `CommandKind` unchanged. `register`/`validate_spec` never check namespace
ownership or trust level. Probe H: in an empty registry,
`register_raw("builtin:settings", "Totally Real Settings", CommandKind::Builtin)`
succeeds, prepares, and reports `requires_confirmation=false`. If a legitimate builtin
is registered first, the provider gets `DuplicateCommand`; registration order decides
who owns `builtin:settings`.

Impact: a provider can impersonate trusted namespaces/kinds, block legitimate builtins,
or present an arbitrary host behavior as a non-consequential built-in. `app:demo` with
`CommandKind::Application` and `extension:vendor` with `CommandKind::Builtin` are both
accepted (the latter is used in the crate's own test at `registry.rs:868-878`).

Minimal fix: add an explicit origin/trust field to `CommandSpec` (or separate
trusted/untrusted registration APIs), reserve `builtin:`, `app:`, `quicklink:`,
`script:` and `extension:` namespaces by origin, and reject `Builtin` (and other
reserved kinds) from the raw/untrusted entry point. If `register_raw` is only called by
trusted first-party code, stop documenting it as untrusted.

### MEDIUM detail

**M1 — grants are advisory at the call site.** `execute` takes `&GrantSnapshot` from the
same caller that holds the `Authorization`. Probe C: prepare and authorize with a real
snapshot, then execute with a newly constructed all-granted snapshot → `Completed`,
`host_performs=1`. A caller can equally reuse the snapshot captured at authorization
time after the real permission store revokes it. Forged `Authorization` values are
prevented by private fields/constructors, but grant authority is not anchored in the
registry or host. Fix: accept a trusted `GrantSource`/permission-provider (or have
`Host::perform` verify), or bind the authorization to a fresh snapshot and document the
caller contract. This is trust-boundary-dependent; in-process callers are already
powerful.

**M2 — reference failures are mislabeled as input errors.** `authorize` and `execute`
use `ActionError::InvalidInput { field: "action_ref" }` for foreign, stale, or
cross-command references (`registry.rs:244-260`, `:313-343`). `ErrorCode::InvalidInput`
has the stable remedy "Check the value for the highlighted field" (`error.rs:75`), which
is wrong for an opaque reference. The ticket requires a stable, correctly mapped
taxonomy; this is the one clear mis-map. Fix without expanding the seven codes: use
`Conflict` for same-registry stale/cross-command references and `MissingTarget` for
unknown/foreign ones, reserving `InvalidInput` for parameter binding; or add a dedicated
reference code and update the table/tests.

**M3 — unbounded lifecycle maps.** `prepared` (keyed by sequence), `operations` (keyed
by `OperationId`) and `action_operations` (keyed by `ActionRef`) are never pruned; there
is no cancel/discard API. A caller can prepare repeatedly (probe A does two) and never
execute; each prepare retains typed parameters and target for the process lifetime
(`registry.rs:205-216`). A long-running launcher leaks per preview, and the ticket's
"auditable" lifecycle history has no retention policy. Fix: add `discard`/`cancel` for
unexecuted actions, cap retention for completed operations (with a bounded replay
tombstone), or document an explicit registry recreation policy. `PreparedAction` is `Clone`, so
drop-based cleanup cannot be relied upon.

### LOW notes

* **L1** is theoretical (2^64 allocations) but `saturating_add` is the wrong failure
  mode for an authority identifier. Use `checked_add` and return a typed "registry
  exhausted" error, or a wider sequence. The same applies to `NEXT_REGISTRY`.
* **L2** probe K: `app:nul` with title `"T\0X"` and choice option `"a\0b"` registers and
  binds. Only `validate_target` (`command.rs:147-159`) and path defaults reject NUL.
  At minimum decide whether display fields must reject control characters; otherwise
  the UI/log/host must sanitize. Titles, keywords and command IDs also have no length
  bound, unlike parameter names/values/options.
* **L3** is cosmetic but makes telemetry grouping awkward; add `TooManyParameters`.
* **L4** is partly a domain issue: `CommandId::parse` accepts arbitrary non-whitespace
  Unicode including U+200B, and comparisons are byte-exact. Define a normalization/case
  policy in `ansa-domain`, or state explicitly that IDs are opaque bytes and UIs must
  never group/display them as text.
* **L5** test gaps that matter: prepare-twice, prepare-after-uncertain, kind/capability
  invariants, `HostReport::{Unsupported,Missing,Conflict,Cancelled}` mapping, all
  `ActionError` variants in the map test, NUL/control strings, and choice/parameter
  count boundaries. The existing tests are correct; they are narrower than their names.
* **L6** add the `action_operations` guard to `authorize` (return `Conflict`/`Uncertain`)
  and move it before the target probe/grant checks in `execute` where appropriate. This
  also avoids host probes for replays. It does not permit an effect today.

## Verified vs not verified

**Verified (by reading, unit tests, and probes):**

* Registration is atomic on failure and duplicate/malformed ID handling is exact.
* Parameter schemas are validated at registration and bound before any action record is
  created; defaults and choice membership are checked; unknown/missing/malformed/
  oversized values are rejected; typed values cannot be constructed externally
  (`ParameterValues` fields private, `PreparedAction::new`/`ExecutionRequest::new` are
  `pub(crate)`).
* Execution identity is `CommandId` only; titles are used only for display summaries.
* Cross-command, stale-revision, missing-target and foreign-registry references are
  rejected before `host.perform`; `Authorization` is not externally constructible.
* Same-token replay after `Completed`/`Uncertain` is blocked; `reconcile` maps
  `StillPending`/`Unknown` without marking success and reports `Completed` without a host
  call for an already-completed operation.
* `ErrorCode` table is stable and exhaustive for `ActionError`; all seven codes have
  stable strings/remedies.
* Bounds: max 64 parameters, 64 choice options, 64 name chars, 4096 value chars are
  checked before iterating adversarial collections; no panic was found in the fuzz
  tests or probes.
* `cargo test`, Clippy `-D warnings`, and fmt all pass.

**Not verified / not implemented:**

* End-to-end integration with `crates/core`/`coordinator`/`action_panel.rs`. The new
  registry has no caller in the workspace (grep found none); `action_panel.rs` still uses
  its own `ActionId` model. The claim that this is the "single execution path" is a
  design claim, not an integrated fact.
* A real UI actually displaying the `Effect` before confirmation; the registry only
  exposes it.
* OS-level/host-level atomicity between `probe_target`, grant checks and `perform`
  (TOCTOU window). The host must revalidate and fail closed.
* Permission revocation *during* `perform`; only a snapshot passed to `execute` is
  checked (M1).
* Crash/restart durability. The registry is in-memory only; `record_operation` happens
  after `host.perform` returns. A crash in that window loses the uncertain operation, so
  a post-restart retry can duplicate an effect. `OperationId`s are not safe to persist
  across process restarts (instance counter resets); docs say "in memory" only.
* Concurrency (the API takes `&mut self`; no loom/thread tests), real hosts, real files,
  and scale/perf beyond the small unit fixtures.
* No audit sink or lifecycle event stream; `operations` only exposes status through
  `reconcile`, not who/when/authorization details.

## Residual risks

1. **Trust boundary is in-process.** `Confirmation::Confirmed` and `GrantSnapshot` are
   caller-asserted values. A caller can call `authorize(..., Confirmed)` without a human
   and can construct an all-granted snapshot at execute. The token prevents accidental
   replay, not a malicious in-process caller. UI/host must be the real enforcement point
   (M1).
2. **TOCTOU after the last guard.** Target revision and grants are checked immediately
   before `host.perform`, but another thread/process can change the target or revoke a
   grant afterwards. `HostReport::Conflict`/`Denied` is the only recovery, and a
   misbehaving host can still leave an unknown effect.
3. **Unknown outcomes are lost on crash.** No durable operation journal; see "Not
   verified" above. If the launcher restarts after an effect but before
   `record_operation`, the user can be offered the action again.
4. **Display text is unbounded/unfiltered.** Titles/keywords and host-returned target
   identities can contain control characters (L2). UIs must sanitize; the registry does
   not.
5. **Identity hygiene depends on `ansa-domain`.** Case/Unicode/invisible-character
   equivalence is not normalized (L4); a provider or future catalog must not join on
   display text or case-folded IDs.
6. **Retention.** Long-running registries grow without bound (M3); a production host
   needs a restart/eviction policy before shipping.
7. **The crate is not wired in.** The existing `action_panel.rs` gate is
   snapshot/token-based and has no `CommandId` execution handoff; an integration review
   is still required to confirm that panel → registry → host does not reintroduce stale
   selection or display-text identity.

### Acceptance and verdict

* **No BLOCKER or HIGH findings remain.** The original H1/H2/H3 and M1/M2/M3 findings are
  resolved for their stated normal scenarios, and the corresponding tests/probes pass.
* **ANS-14 is acceptable at the crate/API level**, subject to the residual risks below.
  R1 (provider provenance) and R2 (Unknown→StillPending) are MEDIUM trust-boundary/edge
  issues that should be fixed or explicitly documented before a real provider/host is
  wired in. They do not invalidate the ticket's normal acceptance path: H1 blocks fresh
  preparation on `Uncertain`, keeps it on `StillPending`, clears it on
  `Completed`/`Failed`/`Unknown`, and re-checks authorization/execution ordering.
* **Not production-ready as an integration:** the crate still has no caller in the
  workspace, no durable operation journal/crash handling, no real UI display gate, and
  no host-level atomicity between probe and perform.

### Residual risks after the fixes

1. **In-process trust remains the outer boundary.** `Confirmation::Confirmed`, the
   `GrantSnapshot` (including its revision), and the `provider_namespace` argument are
   caller-asserted. The registry prevents forged tokens and accidental stale snapshots
   only when a trusted host supplies revisions and the correct provider namespace; it
   cannot authenticate a malicious in-process caller (R1/R4).
2. **Unknown is treated as resolved for blocking but not for history.** A host that
   changes its answer from Unknown to StillPending can leave new intents unblocked (R2);
   unknown/failed actions can permanently consume prepared capacity (R6).
3. **TOCTOU and crash windows remain.** Probes/guards run immediately before
   `host.perform`, but the target or permissions can change during `perform`; a crash
   between the effect and `record_operation` loses the operation. The host must fail
   closed; no durable journal exists.
4. **Display and target hygiene is incomplete.** Zero-width/bidi characters are rejected
   in command IDs but not in titles/keywords/targets; Text input still accepts control
   characters (R5). UIs/logs must sanitize.
5. **Catalog and integration are unbounded/absent.** `specs` has no cap (R8), and the
   registry is not wired to `action_panel.rs`/`coordinator`; end-to-end identity and
   display-before-confirmation remain unverified.
