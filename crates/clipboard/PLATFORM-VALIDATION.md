# Clipboard capture platform validation (P04a / P04b)

Status: macOS AppKit and Linux X11/Wayland adapters are implemented and
cross-target compile checks pass. **No native macOS, X11 or Wayland acceptance
has been performed in this environment.** The host was Windows; real clipboard
servers, Keychain/Secret Service, compositors and desktop policies were not
available. Do not close either ticket on the strength of the results below.

The readers are pull-only. For history, call `ClipboardStore::capture_current`
so locked, paused and private-mode stores do not request native payloads. The
host must stop polling on OS lock and call `store.lock()`; it must also drop any
decrypted previews or content it owns. Neither probing capabilities nor
obtaining a snapshot alone is evidence of a successful capture. This work does
not wire a desktop polling or lock-event handler.

| Transport | Text | Files | Image | Attribution |
| --- | --- | --- | --- | --- |
| macOS AppKit | `public.utf8-plain-text`, subject to OS pasteboard access | `public.file-url` per item, local URLs only | Unsupported; pixels never requested | `NSWorkspace` frontmost bundle ID, Probable or Unknown |
| Local X11 | `CLIPBOARD` with XFixes ≥ 2 and usable `TARGETS`; UTF-8 MIME, `UTF8_STRING`, or valid UTF-8 `text/plain` | `text/uri-list` with local file URLs | Unsupported; pixels never requested | Focused window's `_NET_WM_PID` resolved to the executable basename, Probable or Unknown |
| Native Wayland (one seat) | A compositor that exposes `ext-data-control-v1` or `wlr-data-control-unstable-v1`; same UTF-8 forms as X11 | `text/uri-list` with local file URLs | Unsupported; pixels never requested | Unknown: neither data-control protocol identifies the source app |
| Wayland without an accessible protocol or single seat | Unsupported with a reason; no XWayland fallback | Unsupported with a reason | Unsupported | Unknown |

Linux capability checks are runtime checks, not desktop brand checks. GNOME,
KDE and wlroots versions/policies differ; an XWayland `DISPLAY` does not make a
Wayland session supported. An inherited `WAYLAND_SOCKET` alone is not shared
with this reader; it needs an independent compositor socket. Remote X11,
primary selection, drag-and-drop, legacy encodings, mixed remote file lists,
file promises and rich/image payloads are outside this slice.

## Privacy, limits and lock behavior

- macOS recognizes `org.nspasteboard.ConcealedType`, `TransientType` and
  `AutoGeneratedType` (all with the `org.nspasteboard.` prefix), including
  markers on another item, plus the historical TransientPasteboardType and
  1Password markers. Linux recognizes `x-kde-passwordManagerHint` by presence
  on X11 or Wayland. **Linux has no universal sensitive clipboard marker.**
  Unmarked offers still receive the built-in/content policy scan. App
  exclusions are best effort and cannot match an unknown source. X11 clients
  sharing a display are not a security isolation boundary.
- Privacy markers short-circuit before requesting representation data.
  Configured MIME exclusions can match secondary advertised types, known
  macOS MIME aliases, and base MIME types with charset parameters. Supported
  file representations take precedence over text: malformed, rejected or
  oversized files are not captured as fallback text. A marker-only snapshot is
  payload-free and is rejected as `MonitorProcessingExcluded` by
  `ClipboardStore::capture`.
- Native adapters cap UTF-8 text and file-list wire data at 512 KiB, lists at
  1,024 paths, each decoded path at 32 KiB and each advertised offer at 256
  distinct formats of at most 256 bytes each. No prefix is accepted when
  over-limit, incomplete or undecodable. Store policy can impose lower limits.
  AppKit may allocate `NSData` internally before exposing its length and may
  wait for a lazy provider; its public API does not expose a streaming length
  preflight or transfer deadline. Rust-owned snapshot payloads and scratch
  copies are bounded. Linux native protocol operations use a shared one-second
  socket/transfer deadline per probe or capture, no shell or helper processes,
  bounded X11 property replies and incremental chunks (4,096 events, 1,024
  chunks), and a Wayland pipe that requires EOF (512 KiB plus one byte probe).
  The X11 setup path treats `XAUTHORITY` as optional. A preflight predicate
  passes the path to the pinned xauth reader only when a metadata check sees a
  regular file of at most 64 KiB. That predicate is not an I/O guarantee: the
  pinned reader re-resolves, blocking-opens and reads the path after the check
  without a byte cap, so a path swap, file growth, FIFO substitution or slow
  filesystem can still block or exceed the size hint. The clipboard stream also
  checks the deadline before and after every successful read and write, so an
  always-readable transport cannot extend a capture past its one-second budget
  without polling.
  The Wayland reader also bounds registry globals (1,024), pending offers (8)
  and announced formats (256).
- An X11 payload conversion is requested under `XGrabServer`: the server
  performs `GetSelectionOwner` against the expected owner, scans any
  already-queued XFixes ownership notifications for this monitor and
  `CLIPBOARD`, and only then queues `ConvertSelection` before the grab is
  released. Because requests are server-ordered, the owner reply guarantees
  that a reassertion the server processed before the grab took effect has
  produced an event; a peer request merely queued elsewhere is not covered.
  The scan stops at the first matching notification and rejects it as
  `ClipboardChanged` even when the same window ID reasserted the selection;
  later events remain queued for the next `sync_selection`. Reaching the
  4,096-event application bound without a match also rejects as
  `ClipboardChanged`, because absence cannot be proven; no conversion is sent
  in either case. The local XFixes generation advances on rejection, so a
  same-XID reassertion cannot reuse the previous capture's sequence token.
  `XGrabServer` has no reply: its void cookie is checked for a protocol error
  and the owner round trip proves the grab was processed; the core protocol has
  no separate grab acknowledgement. A new owner cannot receive a payload
  request derived from the previous owner's `TARGETS`, and the grab is not held
  while payload bytes are read. XFixes generation checks still discard a
  snapshot whose ownership changed.
- Automatic insertion re-observes the target last, then checks the clipboard
  sequence and ownership immediately before `send_paste`. The host receives the
  expected sequence so its own checked paste boundary can reject a newer user
  copy. This narrows, but cannot eliminate, the unavoidable gap between the last
  check and the OS input event.
- A macOS `changeCount` transition, X11 XFixes change (even the same owner
  window reasserting ownership), or replaced Wayland data-control offer
  invalidates an in-flight capture. Native generations are scoped to the live
  adapter process/connection; persisted bare desktop counters cannot suppress
  a different copy after a reset. Reopening the same store within a live
  adapter or locking/unlocking does not replay a stored generation. After an
  adapter process restart or compositor reconnect there is no proof the first
  offer is unchanged, so it can be captured once again. Nothing is
  fingerprinted from clipboard plaintext.
- The platform vault seals accepted contents before metadata commit. An
  explicitly passphrase-backed vault can unlock through
  `ClipboardStore::unlock_with_passphrase`. An explicit memory-only vault
  keeps both metadata and payloads off disk and forgets history on lock; there
  is no fallback to unsealed storage. A failed unlock leaves the store locked.
  Disk metadata never contains file paths, text, MIME strings or offered type
  strings. Rejected content creates no history row, sealed payload or preview
  cache entry. In memory-only mode the vault budgets hex-encoded ciphertext,
  which exceeds the plaintext history budget. Capture estimates the encoded
  envelope and selects unpinned candidates, updates candidate metadata and
  victim tombstones only in memory, then calls a transactional vault
  replacement. That replacement seals the new envelope first, checks the exact
  encoded byte/count budget after subtracting the victims, and removes the
  victims only if the new payload fits; a failed seal restores the pre-capture
  history and manifest in memory and leaves every prior ciphertext intact. The
  volatile-budget path never has disk metadata. Persistent backends keep the
  established seal-then-delete protocol and never enter this path. Pinned rows
  are never evicted, and a capture whose only room is a pinned row is rejected
  as `QuotaExhausted`.
- The cross-process store lock is a no-share `CreateFileW` handle on Windows,
  an advisory kernel `flock` on Linux and macOS, and an exclusive-create file
  on other Unix targets. Linux and macOS release the lock on process
  exit/crash; the lock file is intentionally left in place so a concurrent
  opener cannot lock a different inode. Only the other-Unix fallback removes
  the file on drop and can retain a stale lock after a crash.

## Final-review fixes (2026-11-23)

The following defects from `docs/reviews/platform-batch-final-review.md` were
addressed inside `crates/clipboard/**` only:

- **HIGH 2 (X11 protected-offer owner race).** `linux/x11.rs` now wraps the
  expected-owner check and `ConvertSelection` in `XGrabServer`/`UngrabServer`.
  `GetSelectionOwner` must still equal the observed owner before the conversion
  is queued, so another client cannot install a new owner between the check and
  the payload request. The grab is released before the requestor waits for
  `SelectionNotify` or reads any property. XFixes generation checks and the
  one-second deadline are unchanged. A synthetic `SelectionServer` fixture
  changes ownership immediately after the owner query and asserts the new owner
  receives zero conversions; a no-grab control reaches the new owner, proving
  the fixture detects the original race. Tests are Linux-only and were
  compile-checked here, not executed.
- **MEDIUM 1 (bounded X11 setup).** `DeadlineStream::read` and `write` check the
  deadline before and after successful I/O, so a transport that is always
  readable or writable cannot satisfy an unbounded sequence of operations past
  the deadline. The setup path consults `XAUTHORITY` only after a preflight
  metadata predicate accepts a regular file of at most 64 KiB; that predicate
  does not bound the pinned xauth reader's later re-resolution/open/read, which
  has no byte cap (see the residual risk below). The setup path checks the
  deadline again after the authority read. Linux-only unit tests cover the
  expired always-readable socket, a live deadline read, and the authority-size
  predicate.
- **MEDIUM 5 (stale final clipboard observation).** `insertion.rs` now performs
  the final target observation first, then rechecks the clipboard sequence and
  ownership immediately before `send_paste`. `send_paste` also receives the
  expected sequence so a host-side checked paste boundary can reject a newer
  copy. The fake host changes the sequence or owner during the final observation
  and the test requires zero paste attempts.
- **MEDIUM 6 (memory-only encoded budget).** Memory-only history budgets
  plaintext while the vault budgets hex-encoded ciphertext. `store.rs` estimates
  the encoded envelope for every candidate and evicts the oldest unpinned rows
  until the volatile budget is estimated to fit. The final eviction is now
  committed by the vault's transactional replacement (see the second fix pass
  below), not by deleting ciphertext first. Pinned rows are never evicted for
  this budget. A default-limit test with synthetic non-sensitive 128 KiB
  snapshots captures past the 64th item, keeps a pinned row, decrypts the
  pinned row's exact plaintext, and checks the newest payload length.

## Second fix pass — HIGH 2 remainder, R3 (2026-11-23)

The following findings from `docs/reviews/platform-batch-fix-review.md` were
addressed inside `crates/clipboard/**` only:

- **HIGH 2 remainder (same-XID X11 reassertion).** `linux/x11.rs` scans
  already-queued XFixes ownership notifications for the monitor and `CLIPBOARD`
  *under the grab*, after the `GetSelectionOwner` round trip and before
  `ConvertSelection`. The owner reply is a server-ordered barrier: any
  reassertion the server processed before the grab took effect has already
  produced an event by then; a request merely queued by a peer is not covered.
  The scan stops at the first matching event, so later events
  remain queued for `sync_selection`; a match aborts with `ClipboardChanged` and
  zero conversions, even when the same window ID reasserted the selection,
  which the XID comparison alone cannot detect. If the 4,096-event application
  bound is reached without a match, the conversion is rejected as
  `ClipboardChanged` rather than an unclassified limit, because absence cannot
  be proven. The `XGrabServer` void cookie is checked for a protocol error and
  flushed; the core protocol has no separate grab acknowledgement, so the owner
  round trip is the ordering proof. The local XFixes generation advances on
  both rejection paths so a same-XID reassert cannot reuse the previous
  capture's sequence token. The synthetic `SelectionServer` models queued and
  post-release reassertions; tests assert the same-XID abort, the XID-change and
  no-grab controls, a match at the event bound with later events retained, a
  bound overflow without a match, generation invalidation, and that a
  post-release reassertion is not routed to the new offer. Tests are Linux-only
  and were compile-checked, not executed.
- **R3 (failed volatile capture deleted history).** The vault gained
  `put_secret_replacing(alias, secret, remove_aliases)`, a memory-only
  transaction that validates every alias, seals the new payload first,
  computes the exact encoded-byte and count budget after subtracting the
  removals, and mutates the map only if it fits. `SealBackend` gained
  `seal_replacing`; `VaultBackend` calls the transaction, while backends
  without a quota keep the default `seal` behavior. `ClipboardStore::capture`
  updates the candidate metadata and victim tombstones in memory, then passes
  the victims to `seal_replacing`; on failure it restores the pre-capture
  history and manifest in memory, returns `Skipped(QuotaExhausted)` for
  quota/count errors, and leaves every vault entry intact. The volatile path is
  non-persistent, so it has no disk history or manifest and no final metadata
  write that can fail after the victim is removed. The public-path regression
  fills a memory-only vault with unrelated secrets, stores a small row, then
  rejects a 128 KiB row and proves the small row is still decryptable.

## Third fix pass — event-bound generation, mixed volatile/disk (2026-11-23)

The two remaining code defects from
`docs/reviews/platform-batch-fix2-review.md` were addressed inside
`crates/clipboard/**`:

- **X11 event-bound generation loss.** `drain_selection_events` now stops at
  the first matching XFixes notification and returns immediately, leaving later
  events queued for `sync_selection`. If the 4,096-event application bound is
  reached without a match, it returns `ClipboardChanged` instead of
  `CaptureLimit`; `request_conversion` therefore sends no conversion and
  `transfer` advances the ownership generation on both rejection paths. The
  synthetic server models unrelated events, a match at the 4,096th position,
  post-match events left queued, and a bound overflow with no match.
- **Mixed volatile-budget backend and disk metadata.** `open_with_backend` now
  checks `SealBackend::encoded_memory_limit()` before any filesystem access. A
  backend that reports an encoded budget at open is constructed exactly like a
  memory-only vault in `ClipboardStore::open`: no directory validation,
  creation or locking, `is_persistent() == false`, and no `history.json`,
  `manifest.json` or `.lock`. This removes the mixed configuration in which a
  successful transactional eviction followed by a failed final history write
  could lose a valid victim. Backends without an encoded limit, including the
  `MemorySealBackend` test double, keep the persistent store-metadata behavior.
  Because the
  embedding trait does not require the budget to stay stable, `capture` also
  rejects a budget that appears after open on a persistent store with
  `InvalidArgument` before any metadata or payload mutation; a regression toggles
  such a backend after a stored row and proves the row, payload and disk
  metadata are unchanged. The only in-tree caller that previously reached the
  mixed mode was the clipboard pressure test; production `ClipboardStore::open`
  uses `open_with_backend` only for persistent vaults, which report no encoded
  limit, and the other direct callers are tests using `MemorySealBackend`. A
  regression asserts that a volatile-budget backend stores two rows through the
  eviction path without creating any store file, and that its metadata
  persistence calls are no-ops.

Remaining risks for these fixes:

- The X11 grab is a server-ordering guarantee, not end-to-end proof that the
  old owner's response is trustworthy. A malicious owner can still answer with
  arbitrary bytes; filtering and XFixes still apply. If another client already
  holds a server grab, this request waits on the same one-second deadline and
  the session is discarded. No real X server was available here.
- The `XAUTHORITY` regular-file/64 KiB check is a preflight predicate, not an
  I/O guarantee. The pinned xauth reader re-resolves, blocking-opens and reads
  the path after the check without a byte cap. A same-user path swap, FIFO
  substitution, file growth or a pathological filesystem can still block or
  exceed the size hint; the deadline is checked only after the read returns.
- The final insertion check and `send_paste` remain separate operations. The
  host must enforce the expected-sequence check at its own paste boundary; no
  production input-injection adapter is wired.
- The memory-only estimate assumes the vault's current encoded framing
  (hex-encoded nonce/tag plus a 64-byte conservative allowance). A future vault
  framing change could make the estimate low. Other secrets sharing the same
  volatile vault also consume the budget, which this store cannot see, so a
  capture can still be rejected as `QuotaExhausted` even after evicting every
  unpinned row. That rejection is clean: the transactional vault replacement
  leaves the victims, the rest of the history and the retained payloads intact.
  Production memory-only stores have no disk metadata, and `open_with_backend`
  now disallows the mixed disk-metadata/volatile-vault configuration by
  constructing a non-persistent store whenever the backend reports an encoded
  memory budget, so there is no final history write to fail. Persistent
  backends do not take the volatile precommit/replacement path.
- The X11 drain's 4,096-event bound is an application-side cap, not a bound on
  what x11rb buffers while waiting for replies. Reaching the cap without a
  match now invalidates the offer and advances the generation; this is
  conservative and may reject an unchanged offer under a very large event
  backlog. No real X server was available to exercise the cap.
- The same-XID X11 reassertion fix is a server-ordering guarantee, not proof
  that the old or new owner's bytes are trustworthy. A malicious owner can
  still answer with arbitrary bytes; filtering and XFixes still apply. The
  drain uses the owner reply as the barrier because the core protocol has no
  grab acknowledgement; a buggy or non-conforming server that reorders events
  and replies could weaken that barrier. No real X server was available here.

## Residual risks and unsupported cases

- Native acceptance is absent. The macOS adapter has never talked to a real
  pasteboard server; the X11/Wayland adapters have never talked to a real
  X server or compositor. Cross-target clippy/check cannot prove protocol
  behavior, compositor policy, permissions or lazy AppKit providers.
- macOS `NSPasteboard` may allocate a representation or wait for a lazy
  provider before the adapter can inspect its length; there is no native
  transfer deadline. A malicious or hung provider can delay a capture.
- Linux has no universal sensitive marker. An application that does not set
  `x-kde-passwordManagerHint` is protected only by configured exclusions and
  content heuristics. X11 clipboard peers are same-user/display trust peers,
  not an isolation boundary.
- Source attribution is a hint: X11 `_NET_WM_PID` can be spoofed or stale and
  the executable basename can be missing; Wayland is always Unknown; macOS
  reports the frontmost bundle ID, which may not be the copying application.
  Content scanning never depends on attribution.
- X11 ownership can change without an XFixes ownership transition only if an
  owner mutates its own selection in place; that is not detectable without
  fingerprinting plaintext. The same live generation may therefore suppress a
  repeated capture until ownership changes. Wayland has the analogous
  limitation if an offer's data changes without a new selection event.
- The macOS `changeCount` reset behavior of a restarted pasteboard server
  inside one live adapter process is not characterized. A reset to exactly a
  previously observed counter could collide with the in-memory serial map;
  process restart always starts a fresh random generation domain.
- Linux and macOS `flock` is advisory and depends on a local filesystem that
  implements it; network filesystems may not. Other Unix targets still use the
  exclusive-create fallback, so a crash can leave a stale `.lock` that blocks
  the store until the file is removed. The Windows no-share lock is unchanged.
- Memory wiping is best-effort. Plaintext can remain in allocator/Swap/crash
  dumps, in OS clipboard-server memory and, for AppKit, in framework-owned
  `NSData`. The crate does not ship a crash reporter or telemetry and writes no
  clipboard content to logs by construction.
- `history.json`/`manifest.json` are not authenticated. A same-user process
  with write access to the store directory can alter metadata or alias
  ownership; sealed payloads remain vault-encrypted, but the app cannot prove
  metadata integrity against such an attacker.
- Image capture, OCR, file promises, legacy X11 encodings, primary selection,
  remote X11, drag-and-drop and mixed remote file lists are unsupported.
  The crate also does not wire polling or OS lock events; the host must do so.
