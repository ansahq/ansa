# Ranking baseline — 2026-11-19

Status: measured baseline for corpus version `2026-11-19.3`.
Scope: deterministic in-memory command ranking in `ansa-search`, before any
remote provider integration. These numbers are not a claim about an unknown
reference launcher's ranking formula or about real-world query traffic.

## Reproduction

```powershell
cargo test -p ansa-search --test relevance_corpus --offline -- --nocapture
```

The runner prints the corpus version, per-split/per-category metrics, combined
metrics and the pinned floors. It fails on metric regression, an ordered
expectation regression, a category/tier mismatch, or a corpus-integrity error.
The committed corpus is `crates/search/data/relevance_corpus.json`; the runner is
`crates/search/tests/relevance_corpus.rs`.

## Corpus

- Commands: 31.
- Queries: 62 (23 tuning, 39 held-out validation).
- Categories: `exact`, `prefix`, `token`, `fuzzy`, `typo`, `unicode`, `browse`.
- Each query records an ordered expected top-10 list and a note explaining the
  policy it exercises.
- Tuning and validation have separate favorite/usage signal profiles. Signals
  from one split are never applied to the other.
- Non-empty queries are normalized and required to be unique within a split and
  disjoint across splits. `東京` and `東京 駅` are deliberately distinct queries.
- Query categories are checked against the tier that actually produced the top
  result: `exact` accepts exact alias/title, `prefix` accepts title prefix,
  `token` accepts token, `fuzzy`/`typo` accept fuzzy, `unicode` accepts any
  non-browse Unicode match, and `browse` requires fallback.
- The held-out validation split includes deliberately harder cases:
  substitutions and transpositions, ambiguous prefixes, separator noise,
  unaccented diacritics and near-ties. Those queries were added without changing
  ranker code or thresholds to fit their results.
- Four queries are marked `known_failure` because the current subsequence /
  diacritic policy does not satisfy them. They still count in the metrics; the
  flag only suppresses order/tier assertions for an already-documented failure.

The tuning split was not changed by the harder validation work. The validation
split was not used to change ranking behavior.

## Metric and ordering definitions

For one query:

- **Top-1 accuracy** — the first returned id equals the first expected id.
- **Recall@10** — expected ids in the first ten returned ids divided by the
  number of expected ids.
- **MRR** — reciprocal rank of the first returned id that appears anywhere in
  the expected list, or 0 when none appears.
- **Ordered prefix** — the returned rank order must equal the full expected list
  for the first `expected_top10.len()` results. A position-2/3 swap is a failure,
  not merely a metric change. Expected lists are relevance lists, not always ten
  items; recall and ordered checks use the list's actual length.

Category metrics pool all queries in that category within a split. Combined
metrics pool both splits. Split metrics are the CI floors; combined metrics are
reported for context.

## Recency

`SearchSignals` supports timestamped use:

- `record_use_at(id, now)` increments the capped usage count and records the
  newest logical tick for that command.
- `record_use(id)` remains timestamp-free: it increments usage but does not
  create or change recency.
- `recency(id)` is `MAX_RECENCY_SIGNAL - min(age, RECENCY_HORIZON_TICKS)`, where
  `age = now - last_used_at`. Both constants are 100.
- Recency is compared after favorite and usage, so it only reorders rows inside
  an already-selected tier. It cannot cross tiers, and stable `CommandId`
  remains the final tie-break.
- Private mode makes `record_use_at` and recency reads inert. `reset_usage` and
  `reset_all` clear timestamps and the logical tick; `reset_favorites` does not.

Corpus signal profiles use timestamp-free `record_use`, so all corpus recency
values are zero. Recency behavior is covered by deterministic unit tests.

## CI floors and justification

There are two sets of floors:

- **Tuning** — every category and overall at `1.000`, because the tuning split
  is the unchanged policy-derived corpus and any regression there is a defect.
- **Held-out validation** — the measured values from this run:
  - `typo`: top-1 `5/7`, recall@10 `6/9`, MRR `5/7`.
  - `unicode`: top-1/recall@10/MRR `3/5`.
  - `validation overall`: top-1 `35/39`, recall@10 `60/65`, MRR `35/39`.
  - Every other validation category is `1.000`.

These floors are measured, reproducible and intentionally do not claim 100% for
the harder held-out queries. A future change that improves these numbers may
raise the floors; a regression below them fails CI. In addition, the ordered
expected prefix must match exactly for every non-`known_failure` query, so a
swap inside the expected top-10 fails even when aggregate metrics are unchanged.

## Observed held-out failures / known limitations

- `calender` (substitution, `e` for `a`) does not match `Calendar`.
- `termianl` (adjacent transposition) does not match `Terminal` or `Windows
  Terminal`.
- `cafe` does not match `Café`, and `uber` does not match `Über`, because
  normalization preserves diacritics.
- Deletion typos such as `safri` and `spotfy` pass through the fuzzy tier.
- Separator noise (`system--settings`, `time_machine`, `file/explorer/`) and the
  added ambiguous prefixes pass; near-ties follow the documented within-tier
  signals and title/id tie-breaks.
- Perfect tuning metrics remain corpus-local. They do not measure user
  satisfaction, remote-provider recall or performance on a 10k-command catalog.
